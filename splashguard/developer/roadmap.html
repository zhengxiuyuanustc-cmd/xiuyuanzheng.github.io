路线图表示讨论方向，不是已实现功能、发布承诺或保证的时间表。当前公开下载版本以下载站和 GitHub Release 为准；工作分支或 PR 的功能不一定已包含在公开 APK 中。

当前维护范围

  • 所选应用进入前台后的有限开屏处理，准确状态和可暂停的无障碍服务。
  • 广告专用传感器设置的手动引导，不关闭全局方向传感器。
  • 清晰的首次设置向导、可折叠说明和少量可清除的本地记录。
  • 机型指南、严格场景规则、正反例与脱敏样本。

优先改进失败样本、后台状态可见性、更多机型的可复核指引、大字体和读屏可用性。没有出现广告的测试不能作为规则成功证据。

机型指南与验证样本可在机型共建议题 #3认领：记录品牌、型号、系统与应用版本、准确入口和实际结果，提交前去除私人信息与设备唯一标识。

研究议题：应用内广告跳过（不限开屏）

这是独立的 opt-in 实验方向，当前尚未支持。请在应用内广告跳过 RFC #2讨论并认领一个可复现的具体场景，避免多个分支各自做整页泛扫描。

直接将 12 秒延长为几分钟，或对所有页面一直扫描和点击，并不是可接受的实现。应用内广告可能出现在正文、视频、任务、奖励或授权等不同上下文，首先需要确认用户意图和边界。

建议依次研究：

  1. 样本与用户意图：针对单个应用、明确广告组件和自愿开启的场景，整理脱敏正反例；区分用户主动观看的广告与希望跳过的干扰。
  2. 独立开关与生命周期：设计与开屏会话分离、默认关闭、按应用/场景授权的实验开关；明确进入、退出、取消及回调失效条件。
  3. 有限预算与可解释规则：限定时间、次数和候选组件，不把普通内容、付款、授权、导航或奖励操作当作广告关闭目标。
  4. 隐私、性能与耗电：记录需要临时读取的字段，减少扫描范围，检查暂停和锁屏行为，不加入上传、远程指令或未说明的权限。
  5. 模拟与小范围验证：先用纯逻辑测试或受控离线页面验证正反例，再由自愿测试者在指定版本实测；清楚记录失败和未覆盖的情况。

社区可以先提交设计或样本 PR；不必一开始就实现服务。启用正式功能前，由维护者根据可审查证据决定范围、默认值和是否合并，不自动接受陌生分支或未经审查的远程规则。

如何参与一个议题

  1. 搜索现有 Issue，说明希望认领的最小部分、能测试的设备/版本和大致方法。
  2. Fork 后新建 feature/… 或 fix/… 分支，保持一个 PR 解决一个清晰问题。
  3. 提交代码、相应正反例、脱敏证据和验证结果；没有跑通的项目明确写出来。
  4. 接受人工 review 并修订。纯测试 CI 通过只是必要证据之一，不等于维护者已批准或功能已发布。
  5. 由维护者决定是否合并，以及何时发布预览。下载与日常使用不要求参与贡献、注册 GitHub 或打赏；公开提交 Issue / PR 由 GitHub 要求账号。
